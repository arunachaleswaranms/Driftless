# Spike 0.7 — P2P Progressive Watch Proof

**EXPERIMENT ONLY.** This directory is a two-peer feasibility lab, not a production client or protocol.

Serve the repository root on loopback (`python3 -m http.server 4178 --bind 127.0.0.1`) and open `http://127.0.0.1:4178/spikes/phase0/spike-07-p2p-progressive/` in two Chrome tabs. Select **Receiver** and start it in one tab. In the other, keep **Host**, choose a compatible local MP4/H.264/AAC file, and start it. Click **Play receiver** in the receiver tab; the click supplies normal browser user activation. Use **Hold**, **Resume**, **Profile**, and **Seek** to exercise the controlled cases. Close both peers before starting again in the same tabs.

The host needs the Spike 0.5 pinned MP4Box.js dependency installed with `npm ci --ignore-scripts` in `spikes/phase0/spike-05-mp4-segmentation/`. No media belongs in Git. The existing ignored `spikes/phase0/test-media/spike-05/` fixtures are suitable.

## Boundaries

- **Signaling:** same-origin `BroadcastChannel` exchanges SDP and ICE on one development room. There is no server or production room protocol. The peer has no configured STUN/TURN servers, so this lab tests same-host paths only.
- **Host transfer:** Spike 0.6's preparer imports the Spike 0.5 precheck, index plan, bounded `File.slice()` reader, and fMP4 verifier. It cuts one keyframe-aligned segment at a time. An experimental `MEDIA_INFO` precedes two per-track init parts and media parts. Every part is SHA-256 checked, split into 64 KiB payload frames, sent with the Spike 0.3 event-driven `bufferedamountlow` waiter, and released after the receiver's append acknowledgement. Only one part is owned by the transport loop at a time. Successive seek generations join the old source read before a new cut begins.
- **Receiver playback:** it has no source `File`. It bounds and validates one reassembly part, checks SHA-256 and fMP4 structure, and appends per-track init/media to two Spike 0.6 `AppendQueue` instances. Startup uses an experimental two-segment threshold. The receiver removes buffered MSE ranges outside an approximate 30 s back/forward window, never cutting the playhead's contiguous run and never while seeking; a stalled playhead still trims. It does not retain a full-file JavaScript cache or use OPFS.
- **Playback need (scheduling):** host transfer follows the receiver's *current playback need*, not a host read position. `BUFFER_STATUS` carries the receiver's generation, a session-monotonic `seq`, `currentTime`, `contiguousBufferedEnd`/`contiguousAhead` for the buffered run containing the playhead, and `firstMissingSegment` — the segment at that run's end (the *contiguous frontier*), learned from part declarations. Disjoint buffered media elsewhere never satisfies the need or the 20 s ahead cap. The receiver reports on segment completion, at most every 200 ms on `timeupdate`, immediately on every seek, and on `waiting`; identical repeats are suppressed. The host ([`src/scheduling.mjs`](src/scheduling.mjs)) ignores older generations or sequences, rebases its cursor on every accepted need, never sends a segment starting more than 20 s past the reported playhead, and stops re-sending a segment after three deliveries in one generation.
- **Seek:** every seek, local or remote, starts a new receiver generation, because even a buffered seek changes what the host should send next. A seek counts as buffered only if its exact target is inside a buffered range (no start tolerance, because Chrome does not resolve a seek to a target just before the buffered start). An unbuffered seek also sends `SEEK_REQUEST` with the target time, which the host maps through its deterministic segment index; a buffered seek plays locally and sends only the new need. On a newer generation the host aborts obsolete transport work, joins its old cut, and schedules from the new need. Old-generation chunks are discarded, so a local seek can discard at most one in-flight part.
- **Profiles:** FAST 8×, NORMAL 1.5×, CONSTRAINED 0.4× media duration are laboratory pacing factors, not measured network profiles. The host can also pause transport entirely.

The binary frame, control messages, 64 KiB chunk size, 20 s ahead cap, 30 s MSE window, and startup threshold are experiment parameters, not production contracts. There is no upload endpoint, analytics, telemetry, persistent cache, or arbitrary filesystem write. The page's CSP has `connect-src 'none'` and allows media only from its own `blob:` URL.

Run `node --test spikes/phase0/spike-*/src/*.test.mjs` from the repository root for all Phase 0 tests. `scheduling.test.mjs` unit-tests the need model; `scheduling-sim.test.mjs` is a deterministic host/receiver simulation that runs the review's regression scenarios against the real scheduler and against a model of the pre-fix scheduler, which must fail them. See [the result record](../results/spike-07-p2p-progressive.md) for the actual Chrome evidence, gaps, and debt.
